## 0. Structural Decision: ACM/TOSEM Template-Aligned Structure

The manuscript should align with the ACM journal submission workflow used by TOSEM and use a conventional software-engineering article body. ACM's journal author guidance requires ACM authoring templates for journal submissions, single-column review format, the latest Primary Article Template for LaTeX, `\documentclass[manuscript]{acmart}` at review stage, CCS concepts, keywords, ACM reference format, figure descriptions for accessibility, standard ACM reference formatting, and a short description for supplementary online-only material where applicable. ACM also notes that journal articles are ultimately prepared for ACM Digital Library print/digital display and that most ACM journals use the `acmsmall` journal template at publication stage. See ACM Author Gateway: [Submitting Articles to ACM Journals](https://authors.acm.org/journals/submission-process).

Therefore, the paper should use the following **TOSEM-compatible outer structure**:

### Front Matter

1. Title
2. Authors and affiliations
3. Abstract
4. CCS Concepts
5. Keywords
6. ACM Reference Format, generated by `acmart`

### Main Text

1. Introduction
2. Related Work
3. Proposed Method
4. Experiments
5. Result Analysis and Discussion
6. Threats to Validity and Limitations
7. Future Work
8. Conclusion

### Back Matter

1. Data Availability / Artifact Availability
2. Supplementary Material Description
3. Acknowledgments / Funding, if applicable
4. Conflict of Interest / Ethics / AI-use disclosure, if required by the final submission policy
5. References
6. Appendices, if needed

Reason:

The previous 12-section structure was useful as an internal argument map, but it risks making the paper look over-engineered and harder to review. The ACM/TOSEM-compatible structure lowers reading friction while still allowing the paper to carry the same research question:

**How can NOETHER derive broader and more explainable MR class / MetaPattern design spaces from governing-equation operator algebra than expert-experience-based MR sets and search-based MR generation methods?**

The three evidence axes are retained but moved inside standard sections:

1. **Expert MR sets comparison** -> Experiments + Result Analysis.
2. **Search-based method comparison** -> Related Work + Experiments + Result Analysis.
3. **Cross-domain operator-block derivation** -> Proposed Method + Experiments + Result Analysis.

Scope firewall:

The paper remains about **MR identification**, not MR fault-revealing effectiveness. Mutation results, if retained, are secondary executability or sanity-check material and should not define the main claim.

## 1. Introduction

### Goal

Introduce MR identification as the central oracle-side problem, state the research question, and define the paper's contribution as structured MR-class identification rather than MR effectiveness evaluation.

### Purpose for Readers

Readers should understand immediately that NOETHER is a method for deriving and explaining MR classes / MetaPatterns from equation-operator algebra. They should not enter the paper expecting a fault-detection competition against GenMorph or expert-written MRs.

### Content Design

The introduction should follow this order:

1. Metamorphic testing depends on MRs, but MR identification remains difficult.
2. Expert MR sets are useful but often reflect implicit domain intuition.
3. Search-based MR generation can produce candidate relations but may not explain algebraic origin or applicability boundary.
4. Equation-governed program families contain operator-algebraic structures that imply MR classes.
5. NOETHER makes those structures explicit and derives MR classes / MetaPatterns.
6. The paper evaluates structural MR design-space coverage, origin, and boundary.

### Contributions

State contributions as:

1. A program-family model that treats governing-equation operator algebra as a source of MR classes.
2. A NOETHER derivation procedure from operator blocks to MR classes / MetaPatterns.
3. A binary operator-block coverage protocol for comparing NOETHER with expert MR sets.
4. An origin/boundary comparison with search-based MR generation.
5. Cross-domain evidence that the same operator blocks explain MR classes in different program families or solvers.

Do not state contributions as:

1. Higher mutant kill rate.
2. General fault-detection superiority.
3. Replacement of experts.
4. Rejection of search-based methods.

### Acceptance Criteria

1. The final RQ appears explicitly.
2. The introduction contains the scope firewall: MR identification, not MR effectiveness.
3. GenMorph is framed as complementary search-based generation.
4. SACOS/SPARK/LOCUST are introduced as evidence for structural MR identification breadth, not for defect detection.
5. The reader can predict the three evidence axes before reaching the method section.

## 3. Proposed Method

### Goal

Define the NOETHER framework and show how it derives MR classes / MetaPatterns from program-family governing-equation operator algebra.

### Purpose for Readers

Readers should understand what the method takes as input, what it produces, what counts as coverage, and where the boundary lies between identified MR classes and executable MR instances.

### Content Design

Use five subsections:

1. **Problem model and scope.**
   - Define program family, governing equation/operator system, operator algebra, operator block, MR class / MetaPattern.
   - State the two-level model: identified MR class vs executable MR instance.

2. **Operator-block taxonomy.**
   - Present the curated blocks.
   - For each block, state mathematical source, derived MR class form, assumptions, and boundary.

3. **NOETHER derivation procedure.**
   - Distil operator algebra.
   - Decompose into operator blocks.
   - Extract invariants.
   - Translate invariants into MR classes.
   - Check interface affordances for executable instances.

4. **Coverage definition.**
   - Expert coverage = at least one expert MR belongs to the block.
   - NOETHER coverage = at least one explicitly derived MR class belongs to the block.
   - Equation structure alone is not coverage.

5. **Theoretical boundary.**
   - Explain upstream empirical curation and downstream mechanical derivation.
   - State that current blocks are scoped, not universal.
   - Summarize negative/out-of-scope cases without letting them dominate the main text.

### Acceptance Criteria

1. The two-level model is formalized before evaluation.
2. Every operator block is tied to origin, derivation template, and boundary.
3. The method section contains no effectiveness metric.
4. The coverage rules are stated before the experiment section.
5. The method is reproducible enough that another researcher can audit a coverage cell.

## 4. Experiments

### Goal

Define the empirical and documentary evidence used to answer the RQ. The experiments should measure MR-identification coverage, origin/boundary explanation, and cross-domain derivability.

### Purpose for Readers

Readers should see that the evaluation is intentionally designed around MR design-space coverage and explanation, not around fault-revealing effectiveness.

### Experiment Questions

Use three experiment questions:

**EQ1: Expert MR Set Coverage**

Can NOETHER derive MR classes in operator blocks absent from expert MR sets?

**EQ2: Search-Based Comparison**

How does NOETHER differ from search-based MR generation in origin explanation, boundary explanation, redundancy/readability, and maintainability?

**EQ3: Cross-Domain Operator-Block Sharing**

Can the same operator block explain MR classes across different program families, domains, or solvers?

### Content Design

Use five subsections:

1. **Subjects and evidence sources.**
   - Expert MR corpora: SACOS/SPARK/LOCUST and any other clearly sourced expert sets.
   - Search-based comparator: GenMorph and relevant generated-test/oracle literature.
   - Cross-domain derivation subjects: use existing manuscript examples such as Boltzmann/reactor physics, equivariant ML, relational query optimizers, numerical linear algebra, signal processing, or other already-supported cases.

2. **Coverage protocol.**
   - Binary operator-block coverage.
   - Cell-level evidence requirement.
   - Treatment of identified-but-not-executable MR classes.

3. **Search-method comparison protocol.**
   - Origin explanation.
   - Boundary explanation.
   - Redundancy.
   - Readability and maintenance.
   - Human screening burden.

4. **Derivation trace protocol.**
   - For every NOETHER coverage claim, record equation/operator source, block, MR class, assumptions, interface affordances, and evidence location.

5. **Secondary executability checks.**
   - Optional and clearly scoped.
   - Mutation/head-to-head material may be retained only as secondary sanity-check evidence or moved to appendix.

### Acceptance Criteria

1. Experiments are framed as EQ1-EQ3, not as effectiveness hypotheses.
2. Binary coverage rules are restated before result tables.
3. Every subject has a clear role in the RQ.
4. Search-based claims depend on literature or explicit comparator outputs, not unsupported intuition.
5. Mutation or fault-detection material is marked as secondary.

## 5. Result Analysis and Discussion

### Goal

Report and interpret the results for EQ1-EQ3, then discuss what they mean for MR identification, expert knowledge, search-based generation, and program-family testability.

### Purpose for Readers

Readers should be able to verify the paper's main claim: NOETHER broadens and explains MR design-space coverage by deriving MR classes from operator-algebraic origins.

### Content Design

Use five subsections:

1. **EQ1 results: expert MR sets vs NOETHER.**
   - Present binary operator-block coverage.
   - Emphasize structural breadth, not number of MR instances.
   - Discuss SACOS/SPARK/LOCUST as evidence that expert sets can concentrate in monotone/order-style relations while governing equations support broader algebraic origins.

2. **EQ2 results: NOETHER vs search-based generation.**
   - Present origin/boundary comparison.
   - State what search-based methods do well.
   - Explain why generated candidate relations still need interpretation, deduplication, and maintenance.
   - Keep GenMorph complementary.

3. **EQ3 results: cross-domain shared operator blocks.**
   - Present 2-3 cross-domain examples.
   - Show same operator block -> different program families/solvers -> corresponding MR classes.
   - Explain why this supports theory-level transfer.

4. **Boundary analysis.**
   - Discuss identified-but-not-executable classes.
   - Discuss negative/out-of-scope cases.
   - Show that boundaries are part of the contribution.

5. **Discussion.**
   - What changes in how MT models oracle-side testability?
   - Why expert knowledge is made explicit rather than replaced.
   - Why NOETHER and search-based generation are complementary.
   - What this implies for design-for-testability.

### Acceptance Criteria

1. Results are organized by EQ1-EQ3.
2. Every coverage yes/no cell is evidence-backed.
3. Discussion does not infer fault-detection superiority from coverage breadth.
4. Search-based comparison uses literature-supported criteria.
5. Cross-domain examples are grounded in independent mathematical/physical equation sources.
6. Boundary cases are treated as explanatory value, not embarrassment.

## 6. Threats to Validity and Limitations

### Goal

State the validity threats and residual limitations in a form familiar to TOSEM and empirical software-engineering readers.

### Purpose for Readers

Readers should trust that the paper is not overclaiming. They should also recognize that the paper is using the standard software-engineering validity vocabulary rather than a generic "weaknesses" discussion.

### Content Design

Use the title **Threats to Validity and Limitations**, not **Thread to validity**. The word is "Threats"; "Thread" would read as a typo and should not appear in the manuscript.

Use five subsections:

1. **Construct validity.**
   - Binary operator-block coverage measures MR design-space breadth, not MR quality or fault-revealing effectiveness.
   - Expert MR sets may be incomplete records of expert tacit knowledge.
   - LLM-assisted labels and author-derived MR sets require human replication.

2. **Internal validity.**
   - Coverage classification depends on correct assignment of MRs to operator blocks.
   - NOETHER derivations must be traceable to equations/operators rather than post-hoc labels.
   - Search-method comparison must not overstate what the literature supports.

3. **External validity.**
   - Blocks are empirically curated and may require extension.
   - Cross-domain examples support structural transfer across the studied domains, not universal applicability to all programs.
   - Production-code examples may expose only part of the block taxonomy.

4. **Conclusion validity.**
   - The paper should not infer fault-detection superiority from coverage breadth.
   - Mutation/head-to-head material, if retained, is secondary sanity-check evidence.

5. **Limitations beyond validity.**
   - Some identified MR classes require interfaces that existing programs do not expose.
   - Design-for-testability remains an implication and future-work direction.
   - Operator-block taxonomy may need new blocks for mathematical structures outside the current signature.

### Acceptance Criteria

1. The section title is `Threats to Validity and Limitations`.
2. The paper explicitly says binary coverage is not effectiveness.
3. Expert incompleteness and interface limitations are acknowledged.
4. LLM-based evidence is treated as corroborative, not confirmatory.
5. Internal, construct, external, and conclusion validity are all covered.
6. The limitations prepare the future-work section naturally.

## 8. Conclusion

### Goal

Close the paper by restating the theoretical and methodological contribution.

### Purpose for Readers

Readers should remember NOETHER as a framework that explains where MR classes come from, what their boundaries are, and how structured identification broadens MR design-space coverage.

### Content Design

The conclusion should state:

1. MR identification is a central oracle-side problem in metamorphic testing.
2. NOETHER derives MR classes / MetaPatterns from governing-equation operator algebra.
3. The method makes MR origin and boundary explicit.
4. Binary operator-block coverage shows broader structural coverage than expert MR sets in the studied evidence.
5. NOETHER complements search-based generation by adding explanation and maintainability structure.
6. The framework suggests a future design-for-testability path.

### Acceptance Criteria

1. No claim of general fault-detection superiority.
2. No claim that experts are replaced.
3. No claim that search-based methods are unnecessary.
4. The final paragraph returns to MR origin, boundary, and program-family testability.
5. The conclusion mirrors the RQ from the introduction.

### Figures and Tables

No new figure or table.

Reason:

The conclusion should synthesize evidence already shown, not introduce new material.
